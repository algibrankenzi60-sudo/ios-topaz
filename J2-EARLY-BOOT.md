# J2 Prime XNU early-boot audit

## Result

The earlier 0x44000000 RAM candidate and its description were wrong. The captured FDT and the matching G532G MT6737T kernel DTS encode one bank as `reg = <0 0x40000000 0 0x80000000>`, which is the half-open 2 GiB interval `[0x40000000,0xc0000000)`, not a 128 MiB bank. All five retained live DTBs agree. The implementation now selects only `[0x80000000,0x84000000)`, a 64 MiB subset of the separately recorded `/proc/iomem` System RAM interval `[0x80000000,0x9f5c0000)`.

The captured FDT's dynamic `consys-reserve-memory` is 1 MiB, 2 MiB aligned, and has `alloc-ranges = [0x40000000,0x80000000)`, with no fixed `reg`. The new candidate starts at the exclusive end of that allocator range, so it intersects neither that dynamic allocation domain nor any static reserved-memory entry. The board DTS confirms the memory-bank encoding; `of_reserved_mem.c` allocates dynamic reservations from the FDT constraints; the MediaTek callback records the chosen base and uses the area for connectivity EMI sharing. [G532G board DTS](https://github.com/almondnguyen/android_kernel_samsung_grandppltedx/blob/lineage-15.1/arch/arm/boot/dts/mt6737t_grandpplte_cis_ser_04.dts), [MT6735 reserved-memory DTS](https://github.com/almondnguyen/android_kernel_samsung_grandppltedx/blob/lineage-15.1/arch/arm/boot/dts/mt6735.dtsi), [reserved-memory allocator](https://github.com/almondnguyen/android_kernel_samsung_grandppltedx/blob/lineage-15.1/drivers/of/of_reserved_mem.c), [MediaTek consys callback](https://github.com/almondnguyen/android_kernel_samsung_grandppltedx/blob/lineage-15.1/drivers/misc/mediatek/connectivity/common/conn_soc/mt6735/mtk_wcn_consys_hw.c).

The live `/proc/iomem` snapshot is retained outside git at `/mnt/d/J2-iOS-audit-20261027/runtime-iomem-20261028.txt`. It reports `80000000-9f5bffff : System RAM`, containing the selected 64 MiB interval. A fresh, read-only root ADB capture of the running J2 Prime kernel log resolves the dynamic allocation exactly: `consys-reserve-memory : 0x7f800000 - 0x7f8fffff (0x100000)`. The memblock reserved list independently reports the same range. The candidate starts at `0x80000000`, 7 MiB after consys ends, and is outside the DTB allocation window `[0x40000000,0x80000000)`. The log also reports ATF memory reserved at `0x9f5c0000-0x9fffffff`, immediately above the `/proc/iomem` System RAM end; it does not overlap the candidate. Raw read-only snapshots are retained outside git at `/mnt/d/J2-iOS-audit-20261027/runtime-dmesg-20261028.txt`, `runtime-iomem-20261028.txt`, `runtime-memblock-reserved-20261028.txt`, and `runtime-memblock-memory-20261028.txt`. These observations verify the candidate against the current LineageOS boot's allocator state; they do not establish ownership under a different preloader/TrustZone boot path.

## Loader and handoff

The physical MT6737 shim contract is established: the stock loader places its 16 KiB image at `0x40004000`, the shim invokes MediaTek SMC `0x82000200`, and TrustZone enters AArch64 at `0x40008000`. The four-colour framebuffer probe on this handset verifies that the shim reached an AArch64 payload and that the payload could write the display. This proves mode switch and second-stage entry, not the XNU handoff itself. The shim source and build artifact are under `/mnt/d/J2-iOS-audit-20261027/mt6735-bootshim` and `bootshim-build/`.

The J2 second stage is linked at the observed entry. It validates the package and segment table, converts high XNU VAs to physical addresses using a checked offset (`physBase + (VA - virtBase)`), copies each segment, clears BSS, flushes/invalidate data cache for the written ranges, builds a version-2 ARM64 `boot_args` block, maps its ADT pointer back to the XNU VA window, and branches to the Mach-O entry with `x0 = boot_args physical address`. Compile-time layout assertions match XNU 8796's `pexpert/pexpert/arm64/boot.h`. The loader stack is at `0x80f00000`, in the selected RAM window below the kernel's first destination segment; the shim/payload source remains below `0x41000000`.

The kernel package is an uncompressed 4 KiB ARM64 Mach-O with 10 segments and no chained fixups. Kernel, ADT, and boot_args fit the chosen 64 MiB window. The package is separate from Topaz's SWEET format. The 16 MiB recovery-size check remains a packaging limit only.

Latest offline build (`j2prime-earlyboot-audit-20261028`): kernel 16,351,688 bytes (SHA-256 `2d716f57c351f126317970da6512dfe2f9f8eb2354c9b9e672237d5c03818eea`); payload 15,748,992 bytes; combined diagnostic kernel 15,769,472 bytes (SHA-256 `cd05e2188a4653aaa5bc2471335e5c749063b3369ea2f152448784275b839746`). The segments occupy `[0x81004000,0x81fe81c8)`, the page-aligned kernel end is `0x81fe9000`, ADT is at `0x81fe9000`, boot_args at `0x81fea000`, and about 32 MiB of the 64 MiB candidate remains beyond boot_args. The diagnostic artifact stays outside the repository and is labelled not for flashing.

### Offline handoff audit and retained stage marker (2026-10-28)

The kexec control tool submits one page-aligned segment at physical `0x84000000`, with entry `0x84000000`, architecture `KEXEC_ARCH_ARM`, and segment length rounded up to 4 KiB. Its image is laid out as a 16 KiB AArch32 trampoline, one 4 KiB AArch64 loader page, then the Mach-O package at `0x84005000`. The trampoline begins with an ARM branch over its 28-byte metadata header to code at offset `0x20`; its header names the same base, entry, loader, package, and upper bound. Linux's ARM relocation code copies the kexec pages and then enters `image->start` in ARM state with `r0=0`, `r1=machine_arch_type`, `r2=ATAG/DT address`; the trampoline ignores those three values and uses its fixed addresses. This ABI agrees with the reference `relocate_kernel.S` at the [matching G532G kernel commit](https://github.com/RodrigoAyuso/android_kernel_samsung_grandppltedx/blob/d88dd8238d239328549fe74694e43d915703b5ae/arch/arm/kernel/relocate_kernel.S). The exact running Android kernel source is unavailable, so this source comparison is strong but not a byte-for-byte provenance proof.

For that source, `machine_kexec()` prints `Bye!`, optionally calls `kexec_reinit`, and enters `soft_restart`. `soft_restart` changes to a flat mapping, flushes caches, calls `cpu_proc_fin` to disable caches, flushes again, and branches through the physical CPU reset routine; the ARMv7 reset routine disables the MMU before branching to the relocation stub. The sequence is visible in [machine_kexec.c](https://github.com/RodrigoAyuso/android_kernel_samsung_grandppltedx/blob/d88dd8238d239328549fe74694e43d915703b5ae/arch/arm/kernel/machine_kexec.c), [process.c](https://github.com/RodrigoAyuso/android_kernel_samsung_grandppltedx/blob/d88dd8238d239328549fe74694e43d915703b5ae/arch/arm/kernel/process.c), and [proc-v7.S](https://github.com/RodrigoAyuso/android_kernel_samsung_grandppltedx/blob/d88dd8238d239328549fe74694e43d915703b5ae/arch/arm/mm/proc-v7.S). The trampoline therefore expects ARM state with MMU/caches off, which is the state these sources arrange. The `Bye!` pstore line is emitted before `kexec_reinit` and `soft_restart`; it does not prove those calls returned or that the relocation stub reached the image.

The current offline artifact is internally consistent: image SHA-256 `575529d503756fc363995711d5993991d1feb376f2d092d490a8d767eb203c38`; its 16 KiB trampoline, 4 KiB loader page, and 15,748,992-byte package exactly match their component files and manifest hashes, and the package length field matches the embedded bytes. The earlier executed backlight diagnostic was a different artifact (`a60543cc6927a0d181820582a704a74bee6a213ffc1cf0feb019058ea3b3fd15`); its host-to-device copy hash was checked before `kexec_load`. The current stage-marker artifact has **not** been copied to or run on the phone. `kexec_ctl` validates the image metadata and package header but does not independently hash the trampoline on-device, so preserving the host/device SHA check remains necessary.

A read-only query of the running phone reports ramoops `mem_address=0x43f10000`, `mem_size=0xe0000`, `record_size=0x1000`, `console_size=0x10000`, `ftrace_size=0x1000`, `pmsg_size=0x1000`, and `ecc=0`; `/sys/fs/pstore` contained only `console-ramoops`. The matching ramoops layout reserves 190 4 KiB dmesg slots at `[0x43f10000,0x43fce000)`, separate from the two console buffers, ftrace, and pmsg. The new `j2boot/ramoops_marker.c` writes short stage strings only into an empty/invalid dmesg slot, keeps every valid nonempty record untouched, and publishes the record signature last. On reboot, a conforming ramoops backend should expose these as `dmesg-ramoops-*` records. The code scans all 190 slots and writes nothing if they are all occupied. The kernel has no `/dev/mem`, so the raw contents of individual slots could not be independently read; the writer's in-place signature/bounds check is therefore the guard against overwriting a valid record. The slot map follows the live sysfs parameters and the matching `ram_core.c`/`ram.c` implementation; exact kernel source provenance is still unverified. The host test checks allocation/preservation and all-slots-full behavior; it is not an integration test against the handset kernel parser. The prior console record supports warm-reset retention, but does not prove dmesg-slot parsing or that AArch64 can access the physical address under the SMC-provided translation state.

The marker stages distinguish ARM32 trampoline entry, AArch64 loader entry (including CurrentEL and SCTLR_EL1/2 snapshots), loader validation/boot-args completion, and a future XNU call. `XNU_CALL` means only that the loader is about to branch; it is not an XNU-entry marker. No XNU entry instruction has executed. The host-only marker test passes: it preserves an existing valid record, allocates successive free records for the three stages, and makes no change when all slots are occupied. The current diagnostic build still halts before XNU. No new payload was run during this audit, and no partition was touched.

**Last point proven by runtime evidence:** pstore from the previous test contains Linux's `kexec: Starting new kernel`, `Disabling non-boot CPUs ...`, and `Bye!` at uptime 809.316. That proves the kexec shutdown path reached the `machine_kexec()` log point. It does not prove execution of the reset routine, relocation stub, the first AArch32 trampoline instruction, the SMC transition, the AArch64 loader, or XNU. The earlier four-colour recovery probe independently proves the MT6737 SMC can enter a simple AArch64 payload in the recovery boot context, not from Linux kexec.

No GICv2 interrupt delivery, timer tick, confirmed XNU entry, console after the jump, or boot beyond earliest XNU startup has been verified. This remains an early-boot kernel diagnostic, not iOS userspace.


#### Handoff-state limitation found in offline audit

The matching Linux source arranges the kexec relocation entry in ARM state after the ARMv7 reset path disables the MMU and caches. The MT6737 shim source documents only the SMC function ID (`r0=0x82000200`) and target (`r1=entry`) and says the CPU resumes in AArch64; it does not specify destination EL, SCTLR values, translation regime, or cache state. The AArch64 stub currently records `CurrentEL`, `SCTLR_EL1`, and (at EL2+) `SCTLR_EL2`, masks interrupts, selects SP_ELx, and sets a physical stack, but does not normalize MMU/cache state. The loader then dereferences physical addresses directly. Until SMC state is established, neither the AArch64 marker's physical write nor loader's direct map can be certified safe. If later observed, the `ARM64_ENTRY` record will report EL/SCTLR bits; until then, the retained record can prove only ARM32 trampoline entry when that record itself is found. No payload was run to obtain these values.

The payload remains **not ready for a device test**: offline compile, host marker tests, live source-window checks, and byte/hash consistency pass, but the SMC-provided AArch64 state and ramoops dmesg-slot integration are unresolved. The only runtime-proven endpoint remains Linux's `machine_kexec()` `Bye!` log line. Recovery remains the existing force-restart back to Android; no partition or persistent storage is needed or changed by the marker design.
