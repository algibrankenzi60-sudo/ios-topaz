# J2 Prime XNU early-boot audit

## Result

The earlier 0x44000000 RAM candidate and its description were wrong. The captured FDT and the matching G532G MT6737T kernel DTS encode one bank as `reg = <0 0x40000000 0 0x80000000>`, which is the half-open 2 GiB interval `[0x40000000,0xc0000000)`, not a 128 MiB bank. All five retained live DTBs agree. The implementation now selects only `[0x80000000,0x84000000)`, a 64 MiB subset of the separately recorded `/proc/iomem` System RAM interval `[0x80000000,0x9f5c0000)`.

The captured FDT's dynamic `consys-reserve-memory` is 1 MiB, 2 MiB aligned, and has `alloc-ranges = [0x40000000,0x80000000)`, with no fixed `reg`. The new candidate starts at the exclusive end of that allocator range, so it intersects neither that dynamic allocation domain nor any static reserved-memory entry. The board DTS confirms the memory-bank encoding; `of_reserved_mem.c` allocates dynamic reservations from the FDT constraints; the MediaTek callback records the chosen base and uses the area for connectivity EMI sharing. [G532G board DTS](https://github.com/almondnguyen/android_kernel_samsung_grandppltedx/blob/lineage-15.1/arch/arm/boot/dts/mt6737t_grandpplte_cis_ser_04.dts), [MT6735 reserved-memory DTS](https://github.com/almondnguyen/android_kernel_samsung_grandppltedx/blob/lineage-15.1/arch/arm/boot/dts/mt6735.dtsi), [reserved-memory allocator](https://github.com/almondnguyen/android_kernel_samsung_grandppltedx/blob/lineage-15.1/drivers/of/of_reserved_mem.c), [MediaTek consys callback](https://github.com/almondnguyen/android_kernel_samsung_grandppltedx/blob/lineage-15.1/drivers/misc/mediatek/connectivity/common/conn_soc/mt6735/mtk_wcn_consys_hw.c).

The live `/proc/iomem` snapshot is retained outside git at `/mnt/d/J2-iOS-audit-20261027/runtime-iomem-20261028.txt`. It reports `80000000-9f5bffff : System RAM`, containing the selected 64 MiB interval. A fresh, read-only root ADB capture of the running J2 Prime kernel log resolves the dynamic allocation exactly: `consys-reserve-memory : 0x7f800000 - 0x7f8fffff (0x100000)`. The memblock reserved list independently reports the same range. The candidate starts at `0x80000000`, 7 MiB after consys ends, and is outside the DTB allocation window `[0x40000000,0x80000000)`. The log also reports ATF memory reserved at `0x9f5c0000-0x9fffffff`, immediately above the `/proc/iomem` System RAM end; it does not overlap the candidate. Raw read-only snapshots are retained outside git at `/mnt/d/J2-iOS-audit-20261027/runtime-dmesg-20261028.txt`, `runtime-iomem-20261028.txt`, `runtime-memblock-reserved-20261028.txt`, and `runtime-memblock-memory-20261028.txt`. These observations verify the candidate against the current LineageOS boot's allocator state; they do not establish ownership under a different preloader/TrustZone boot path.

## Loader and handoff

The physical MT6737 shim contract is established: the stock loader places its 16 KiB image at `0x40004000`, the shim invokes MediaTek SMC `0x82000200`, and TrustZone enters AArch64 at `0x40008000`. The four-colour framebuffer probe on this handset verifies that the shim reached an AArch64 payload and that the payload could write the display. This proves mode switch and second-stage entry, not the XNU handoff itself. The shim source and build artifact are under `/mnt/d/J2-iOS-audit-20261027/mt6735-bootshim` and `bootshim-build/`.

The J2 second stage is linked at the observed entry. It validates the package and segment table, converts high XNU VAs to physical addresses using a checked offset (`physBase + (VA - virtBase)`), copies each segment, clears BSS, flushes/invalidate data cache for the written ranges, builds a version-2 ARM64 `boot_args` block, maps its ADT pointer back to the XNU VA window, and branches to the Mach-O entry with `x0 = boot_args physical address`. Compile-time layout assertions match XNU 8796's `pexpert/pexpert/arm64/boot.h`. The loader stack is at `0x80f00000`, in the selected RAM window below the kernel's first destination segment; the shim/payload source remains below `0x41000000`.

The kernel package is an uncompressed 4 KiB ARM64 Mach-O with 10 segments and no chained fixups. Kernel, ADT, and boot_args fit the chosen 64 MiB window. The package is separate from Topaz's SWEET format. The 16 MiB recovery-size check remains a packaging limit only.

Latest offline build (`j2prime-earlyboot-audit-20261028`): kernel 16,351,688 bytes (SHA-256 `2d716f57c351f126317970da6512dfe2f9f8eb2354c9b9e672237d5c03818eea`); payload 15,748,992 bytes; combined diagnostic kernel 15,769,472 bytes (SHA-256 `cd05e2188a4653aaa5bc2471335e5c749063b3369ea2f152448784275b839746`). The segments occupy `[0x81004000,0x81fe81c8)`, the page-aligned kernel end is `0x81fe9000`, ADT is at `0x81fe9000`, boot_args at `0x81fea000`, and about 32 MiB of the 64 MiB candidate remains beyond boot_args. The diagnostic artifact stays outside the repository and is labelled not for flashing.

## Offline checks and limits

`j2boot/build-offline.sh OUTPUT_DIR` cross-compiles and links the loader with the installed Android NDK for Windows, audits the FDT, packages the kernel, and composes the diagnostic image from the known 16 KiB shim + loader + package. Audit all five saved live DTBs using:

```sh
for f in /mnt/d/J2-iOS-audit-20261027/live-boot-*.dtb; do
  python3 tools/mkadt_j2.py /tmp/j2prime.adt --dtb "$f"
done
```

The script rejects candidate windows outside captured RAM, overlapping static reservations, or intersecting any declared dynamic allocation range. No QEMU ARM64 executable is installed in this environment.

## RAM-only launch via Android kexec

The currently running LineageOS kernel is `3.18.53-Madness+`, `armv7l`; `/proc/kallsyms` exposes ARM `machine_kexec`/`sys_kexec_load`, `/sys/kernel/kexec_loaded` exists, and `kexec_load_disabled=0`. A small ARM32 probe successfully loaded and unloaded one page using syscall 347, with `kexec_loaded` changing `0 -> 1 -> 0`. Runtime build identity is `#1 SMP PREEMPT Mon Sep 7 18:29:06 -03 2026`, builder `rodrigoayuso@cachyos-x99`; Android identifies as `lineage_grandppltedx-userdebug 8.1.0 OPM7.181205.001 d2f25de76a test-keys`. `/proc/config.gz` is absent and the local `lineage_15_1_j2_prime/Source` directory is empty, so the exact kernel revision/config used for this build is still missing. The [public G532G kernel repository](https://github.com/almondnguyen/android_kernel_samsung_grandppltedx) identifies itself as LineageOS 14.1 and is only a reference until its revision is matched to the running 3.18.53 build.

Added `j2boot/build-kexec-offline.sh`, `kexec_trampoline.S`, `loader-kexec.ld`, and `kexec_ctl.c`. The raw image places a 32-bit trampoline at `0x84000000`; it paints blue, then invokes the already-proven MT6737 TrustZone switch to the AArch64 loader at `0x84004000`. The XNU package starts at `0x84005000`. The image/source window `[0x84000000,0x85000000)` was checked against the live System RAM map and memblock reservations; the kernel's XNU destination window remains `[0x80000000,0x84000000)`. Loader green means it passed package validation and reached the pre-XNU branch; loader red means a validation failure.

On the handset, the final 15,769,600-byte image was copied only to `/dev` tmpfs, verified against host SHA-256 `c3f6d73a6e2642fac03c1b80b522fbf08d28a9ae75190616e2ea0aae6641072b`, accepted by `kexec_load` at `0x84000000`, and unloaded successfully (`kexec_loaded=0`). It was then loaded again (`kexec_loaded=1`) and the explicit Linux `reboot(KEXEC)` request was issued. ADB disconnected, but the user saw no diagnostic color; the phone remained dark for a while, then returned through the Samsung logo to Android. After reboot, `kexec_loaded=0` and `/dev` no longer contained the volatile payload/controller. No partition was written.

The builder identity led to the matching public source repository, [RodrigoAyuso/android_kernel_samsung_grandppltedx at `d88dd823`](https://github.com/RodrigoAyuso/android_kernel_samsung_grandppltedx/tree/d88dd8238d239328549fe74694e43d915703b5ae). Its latest commit is `b96f71fe` (2026-10-01); `d88dd823` (2026-09-05) is the last commit before the handset kernel build date, making it the strongest source match, though the running binary cannot be proven to derive from it. The latest and candidate revisions have identical `arch/arm/kernel/machine_kexec.c` (SHA-256 `01136bcef27b0aff23beeb864928382023f246f19f4e53441ffe042ddc6b74bf`). Its `mt6737t-grandpplte_defconfig` enables `CONFIG_KEXEC`, `CONFIG_HOTPLUG_CPU`, `CONFIG_SMP`, with `CONFIG_NR_CPUS=4`. `machine_kexec_prepare()` validates the segment is RAM and that CPU hotplug is supported; successful `kexec_load` indicates those load-time checks passed. During execution, `machine_kexec()` asserts at most one CPU is online, prints `Bye!`, then calls `soft_restart()`. The ARM relocation code enters the image with `r0=0`, `r1=machine_arch_type`, and `r2=boot-tags address`; the current trampoline ignores those registers, so its entry ABI is compatible with this source.

The first post-test pstore snapshot was stale and unrelated. A later single monitored RAM-only execution produced fresh `/sys/fs/pstore/console-ramoops` (saved outside git as `/mnt/d/J2-iOS-audit-20261027/kexec-pstore-20261028.txt`, SHA-256 `43bd682d64e511a162b54a32d372c663ba067bf9f52f13cecdbb803aa4b2b125`). It records the exact expected sequence at uptime 672.126: `kexec: Starting new kernel`, `Disabling non-boot CPUs ...`, `Bye!`. This confirms userspace invoked KEXEC and Linux entered the architecture handoff through CPU shutdown. Just before that, the shutdown path set display brightness to zero (`ktd3102_backlight_set_brightness: brightness(0)` at 672.083901), so the user's black screen cannot tell us whether the blue AArch32 trampoline ran. There are no panic/oops/watchdog markers in this log, but it ends at `Bye!`; it does not prove the physical reset stub reached `0x84000000`, nor the trampoline, SMC, AArch64 loader, or XNU entry. The phone recovered to Android, `kexec_loaded=0`, and no partition was written. The host disassembly still confirms the ARM32 reboot syscall number `88`, Linux reboot magic values, and `LINUX_REBOOT_CMD_KEXEC` value `0x45584543` are passed in the expected order.

### Assessment

**RAM placement, `kexec_load`, and entry into Linux's kexec shutdown path are verified; the first instruction of the payload is not yet verified.** Windows Minimal ADB and Fastboot at `C:\Program Files (x86)\Minimal ADB and Fastboot` sees serial `4200def9d8929447`, product `grandppltedx`, model `SM_G532G`; root read-only ADB captured `/proc/iomem`, the exact consys allocation, and memblock reservations. The fastboot boot-image artifact remains unsent. Linux fastboot sees no device. Do not repeat a blind execute: the next useful discriminator is instrumentation that survives the panel-off interval (prefer a confirmed UART/debug route or a safe retained-RAM checkpoint); do not guess a UART pin, MMIO address, or memory mailbox. Do not flash either diagnostic image.

No GICv2 interrupt delivery, timer tick, confirmed XNU entry, console after the jump, or boot beyond earliest XNU startup has been verified. This remains an early-boot kernel diagnostic, not iOS userspace.
