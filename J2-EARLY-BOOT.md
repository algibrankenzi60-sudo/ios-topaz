# J2 Prime early boot bring-up (host-only milestone)

This branch now has a separate J2 path in `j2boot/` and `tools/mkadt_j2.py` / `tools/mkpayload_j2.py`. The MT6737 SMC shim remains the AArch32-to-AArch64 transition stage. The added AArch64 second stage is linked at its observed entry `0x40008000`; it checks a J2-specific payload, copies Mach-O segments, zeroes BSS, places the ADT and ARM64 `boot_args`, flushes the instruction cache, then calls the XNU entry with the boot-args physical address. A red framebuffer is the loader's fail-stop indication and green means it passed the package checks immediately before transfer.

The package format is deliberately `J2PRIME\0`, version 1, and 4 KiB aligned. This prevents accidental use by the current Topaz loader (`SWEETXNU`, 16 KiB assumptions). `tools/mkpayload_j2.py` handles the actual ARM64 Mach-O and chained fixups, records all segment file/virtual ranges, and checks RAM/source overlaps. The offline build composes the known 16 KiB MT6737 shim, the second stage, and payload; it rejects a result above the 16 MiB recovery partition. Its result is explicitly diagnostic and must not be flashed.

## Evidence and limits

The captured live Android FDT (`live-boot-88f000.dtb`) declares RAM `[0x40000000, 0x48000000)`. It explicitly reserves `[0x43000000,0x43030000)`, `[0x43030000,0x43031000)`, `[0x43700000,0x43900000)`, `[0x43900000,0x43b00000)`, `[0x43d00000,0x43f00000)`, `[0x43f00000,0x43f10000)`, `[0x43f10000,0x43ff0000)`, `[0x43ff0000,0x44000000)`, and `[0x41e00000,0x42400000)`. Therefore the generated ADT's `0x44000000 + 0x04000000` is inside declared RAM and outside every *static* reservation in that FDT. It also fits the 64 MiB contiguous segment destination: the linked XNU virtual span ends at `0xfffffff007fe9000`, mapping through the tested package to below `0x46000000`.

However, that DTB also has a dynamic reserved-memory node (`size=1 MiB`, alignment 2 MiB, alloc-ranges `[0x40000000,0x80000000)`) without a resolved `reg`. The location selected by the Android kernel is not represented as a fixed reservation in this snapshot. Thus the candidate window is not proven safe from runtime secure/firmware carve-outs. The script reports this risk; no device execution is authorized by the offline build. We need a runtime-resolved reserved-memory map (or authoritative MT6737 memory carve-out source) before treating the candidate as boot-safe.

Other hardware facts carried into the ADT are sourced from the captured J2 FDT and framebuffer probe: GIC distributor `0x10221000/0x10000`, GIC CPU interface `0x10222000/0x10000` (the third `reg` range at `0x10200620` is MediaTek interrupt polarity and is intentionally omitted from the generic GIC node), architected timer at 13 MHz with virtual timer PPI INTID 27, and framebuffer PA `0x7f900000`, 540×960, stride 2176, 32 bpp. `arm-io` child registers are expressed relative to the explicit `0x01000000` bus base. No Topaz address or Apple product identity is emitted.

## Offline result

Run `j2boot/build-offline.sh [OUTPUT_DIR]`. The local check used the verified kernel SHA-256 `2d716f57c351f126317970da6512dfe2f9f8eb2354c9b9e672237d5c03818eea`; it found 10 segments, zero chained fixups, entry VA `0xfffffff00740c488`, produced a 2,492-byte ADT and 15,748,992-byte payload. The combined diagnostic kernel was 15,769,472 bytes (`789a110da11c743847c7b9f2253341cd0f6cb6a96d5bd24acb1087c0ce3c65be`), below the recovery partition size of 16,777,216 bytes. The ARM64 loader cross-compiled and linked at the intended entry. This is source/build validation only: there has been no QEMU execution, no phone boot, and no partition write. Original recovery backup and recovery plan were not modified.

Next technical blocker is resolving dynamic/secure RAM ownership. Then validate the loader contract against XNU's exact bootstrap path under an emulator or controlled temporary boot before any device write. The current ADT intentionally exposes only one CPU and the minimum topology; GIC runtime setup and framebuffer handoff have not been exercised by XNU.
